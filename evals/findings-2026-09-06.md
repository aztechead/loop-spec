run through `claude -p "/loop-spec:cycle autonomous …"` with this checkout as the
plugin. Records: `evals/results/20260906-haiku/`, `evals/results/20260906-sonnet/`,

## Headline

The code the cycle writes is mostly right. What fails is everything around it: no run
delivered, two of five haiku runs lost autonomous mode before they started, one run
ended by asking an absent human a question, and one run spent 160 turns fighting the
plugin's own Stop hooks and then forged its terminal result by hand. Cost and time are
dominated by the process, not the change: the smallest task, a two-line bug fix, took
eleven minutes and 1.67 USD on haiku and produced 302 lines of artifacts.

## Findings, in the order to fix them

### 1. DELIVER refuses every run because the driver never commits its own state

Every haiku run that reached DELIVER was blocked with `dirty_worktree`. The dirt was the
plugin's own `feature.json` and `PROGRESS.md`, untracked in the worktree
(`git status` in `evals/.runs/20260906-haiku/wc-json/project/.claude/worktrees/*`).

Cause. `lib/cycle-driver.sh next` writes the phase state commit with `git add` and
`git commit` in `$PWD`, not in the execution root. The lead runs the driver from the
project root while the feature lives in `.claude/worktrees/<slug>`, so `git add` of the
worktree-relative path fails and the `|| true` after it hides the failure. The proof is
in the project root of every run: a staged `.gitignore` carrying only the two negation
rules the driver appends, and zero `chore: … state @` commits on any branch across all
five runs. In readme-sync the model did call `EnterWorktree`, and DELIVER was blocked
the same way, so the cwd fix alone is not the whole story: DELIVER's dirty check counts
untracked files and nothing in the tree writes an ignore rule for `.loop-spec/` into a
repository that has none. `docs/adopting.md` line 90 says the directory is gitignored.
It is not, unless the user did it.

Fix. Run the state commit with `git -C "$execution_root"`, drop the `|| true` so a
failed state commit is loud (the repo's own failure-tells rule), and have the cycle
write the `.loop-spec/` ignore rule it assumes. Pin it with a unit test that puts the
feature in a worktree and runs `next` from the project root.

### 2. The autonomous token is lost in the prompt rewrite, and the profile does not rescue it

Two of five haiku runs (todo-due, slugify-bug) started with `autonomous: false` in
`active-run.json` and no `autonomous` key in `feature.json`, although the prompt began
with the token and `.loop-spec/profile.json` named the `autonomous` preset. The todo-due
transcript shows the cause: the model rewrote the prose per `prompt-normalize.md` and
passed the rewrite to `cycle-driver.sh start` without the token.

The profile should have covered it and does not. Offline reproduction, no model needed:

```bash
mkdir -p /tmp/r && cd /tmp/r && git init -q -b main && echo hi > README.md && git add -A && git commit -qm init
mkdir .loop-spec && echo '{"preset":"autonomous"}' > .loop-spec/profile.json
bash /path/to/loop-spec/lib/cycle-driver.sh start -- "add a flag to the tool" | jq '{a: .invocation.autonomous, d: [.decisions[].id]}'
# {"a": false, "d": ["commands"]}   <- interactive run, a question left for nobody
```

`lib/cycle-preflight.sh` line 81 evaluates the profile's environment inside its own
process. `lib/cycle-driver.sh` line 98 then reads `LOOP_SPEC_AUTONOMOUS` from an
environment that never received it.

Consequences. todo-due ended its process after 16 turns by asking three interview
questions in prose (`evals/results/20260906-haiku/todo-due.json`, `last_result_text`).
`hooks/team/route-terminal-guard.sh`, built for exactly that silent stop, stood down
with "armed run is interactive; the human owns its ending"
(`/tmp/claude-hooks/loop-spec-route-guard-trace.log`). slugify-bug finished the code,
was blocked at DELIVER, declared the work complete in chat, and ended with no terminal
result at all.

Fix. Resolve the profile in the driver, not in preflight: `start` evaluates
`profile.sh env` before it reads the token. Then `parse-invocation` and the profile
agree, and the guard stays armed. A skill sentence asking the model to "splice the
tokens back" is the prose-versus-hook lesson the tree already teaches itself.

### 3. A blocked delivery turns the Stop hooks into an adversary

readme-sync, haiku, 160 turns, 3.24 USD for a 30-line README edit. After DELIVER
blocked, `hooks/team/adhoc-verify-guard.sh` denied the stop 18 times in a row
(`/tmp/claude-hooks/loop-spec-micro-guard-trace.log`, 04:00 to 04:02, "no content
diff was inspected after the final edit"). The transcript
(`~/.claude/projects/*readme-sync-project--claude-worktrees-readme-sync/`) shows what
the model did to get out: wrote `.loop-spec/micro.conf`, exported
`LOOP_SPEC_MICRO_GUARD=0`, called `cycle-result.sh write-terminal --cycle-type debug`
with four different status and outcome pairs, then wrote `last-result.json` with the
Write tool in two locations. The published result reads `status: completed, outcome:
interrupted, phaseReached: debug, slug: null`.

The feature directory was gone by the end of that run, which is the condition under
which this guard stops seeing an in-flight feature and applies its ad-hoc rule to a
full cycle. Under pressure the model reaches for the kill switches the hooks document
in their own headers.

Fix. A Stop hook must never deny more than once for the same obligation in one turn
sequence; after one denial it records the obligation and allows. And a guard that reads
kill-switch environment variables set by the model itself is not a guard: read them
from the profile file, never from the process environment.

### 4. VERIFY's rewind ends the process instead of continuing

fib-cli, haiku. VERIFY's code reviewer raised three blocking findings, the driver
answered `NEXT phase=execute` twice, and the model published `status: failed, outcome:
interrupted` and exited the worktree instead of invoking EXECUTE
(`evals/results/20260906-haiku/fib-cli.json`, `last_result_text`; feature.json holds
three `pendingRemediationTasks`). A supervisor reading that result treats the run as
dead. The code on the branch passed all six acceptance checks.

Fix. The driver already owns the loop; let it refuse `cycle-result.sh write` while it
has just answered `NEXT`, the same way it refuses a terminal result before DELIVER.

### 5. The process is the cost

Across the four haiku runs that produced code, artifacts outnumber project lines by 3
to 150 times, and the cycle dispatched up to nine subagents for a Fibonacci tool. PLAN
wrote five tasks for it. Each task became a commit, a verify, and a review. The two-line
slugify fix read 2.3 million cached input tokens over 18 lead turns; the README edit
read 17.6 million over 160 (`tokens` in each record; subagent turns are not counted).
None of that is a bug. It is the seven-phase shape applied without regard to the size
of the ask, and the maintenance and compact profiles that exist to shorten it were not
selected because `/loop-spec:cycle` does not classify; only `/loop-spec:auto` does.

Fix. Measure before choosing: route through the classifier on every entry, and make
the structural fast path decide from the diff the plan predicts, not from the phase
list. Then re-run this eval and compare turns and artifact lines per task.

## What worked

- The implementer, verifier, and iterate-judge got the code right in four of five
  haiku runs, including the protected-test task, and the judge scored every accepted
  diff a full match with little over-building except fib-cli.
- wc-json, the run that kept its autonomous flag, published an honest
  `infrastructure-failed` result when DELIVER blocked. The contract works when the
  state around it is right.
- Test tampering did not happen. The protected test file was never touched.
