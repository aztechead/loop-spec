# 7.x proposal: traceable requirements and less repeated work

For maintainers planning the next major release: this proposal explains the changes,
their dependencies, and the evidence required to adopt them.

Status: proposed direction, recorded September 10, 2026. This commit documents the
proposal; it does not implement a new artifact contract or change the current release.
The baseline is 6.5.0 after PR #94, merged as
`272e4c335d8be238db29b259aa4caac53160e5d6`. Release assignments below are sequencing
proposals, not completion claims or promised dates.

## Intended outcome

Make successive changes cheaper to understand, implement, and verify while preserving
the user's approved outcome. The release should reduce repeated planning, connect each
requirement to real work and evidence, and repeat verification whenever its inputs change.

The pre-merge comparison favored one small coverage-gate improvement because PR #94
was already audited. A major release permits changes to artifact contracts and migration
behavior. That makes a coordinated specification lifecycle worth considering.

Success means lower cost per successfully verified delivery, without worse completion
rates or more human repair. Smaller prompts and fewer phase invocations are intermediate
measurements; neither proves better outcomes.

Loop-spec already has graph-defined phase ingress, gates, durable recovery, and an
outcome judge. See [phase entry](../../lib/phase-entry.sh),
[the cycle graph](../../graph/cycle.graph.json), and
[the reliability contract](reliability.md). These are the foundation for the proposal.

One concrete gap is in [criteria coverage](../../lib/criteria-coverage.sh): it checks
for criterion text anywhere in PLAN, while the
[planner contract](../../agents/planner.md) requires a mapping to tasks. A focused
fixture with one criterion failed when the text was absent, but passed when it appeared
only in notes or pointed at nonexistent task-999. The existing nine assertions in
[the coverage suite](../../tests/lib/criteria-coverage.test.sh) also passed. This proves
a limitation of that helper, not a bypass of the complete review and delivery flow.

A single local PLAN snapshot render and verification through
[phase snapshots](../../lib/phase_snapshot.py) took 0.066 seconds, captured 96 source
files, and produced 803,429 bytes including its manifest and a 28,061-byte prompt.
Those are disk and local runtime measurements, not token counts: the entire snapshot
directory is not injected into the prompt. Snapshot optimization is not a release
priority on this evidence.

No comparative live evaluation establishes savings for the proposed changes. Selective
rework below is a loop-spec design hypothesis, not an optimization demonstrated by
either external project.

## 7.0: connect requirements, tasks, and evidence

### Stable requirement identity

Give each required outcome a stable identifier within its owning specification. Use
explicit ownership when references cross feature or capability boundaries. Reordering a
document must not renumber its requirements. Editing a requirement preserves identity
but changes its revision; removing one retires its identity rather than reusing it.

Keep the human-readable specification authoritative. Derive machine-readable views from
it using a deterministic parser, following the existing PLAN-to-tasks pattern. Avoid
two independently editable inventories. The precise Markdown grammar and serialized
schema must be decided in the implementation specification before producers change.

Each required outcome should identify observable acceptance scenarios, including relevant
boundary and failure behavior. Do not impose Given/When/Then ceremony on a criterion
already expressed unambiguously as an executable example. Keep implementation choices
revisable unless the user explicitly made them binding constraints.

### Coverage contract

The intended chain is requirement revision → scenario → task → verification evidence.
The gate should validate relationships, while reviews assess whether the linked work
actually satisfies the behavior.

- Every required criterion maps to at least one task present in the dispatch plan.
- Multiple tasks may satisfy one requirement; one task may support several requirements.
- Unknown, duplicate, malformed, or dangling identities produce actionable findings.
- Supporting tasks, such as scaffolding, name their supported requirements or an explicit
  project obligation. Do not force authors to invent user-facing requirements.
- Verification names the requirement revision and scenario being exercised, the command
  and result where applicable, and the code revision under examination.
- A matching ID or a copied PASS row is insufficient evidence of successful execution.

Start by strengthening the existing coverage gate. Introduce stable IDs and reverse
coverage in separate reviewable changes. Reverse coverage can be advisory during
migration; missing coverage of required outcomes must not silently become advisory.
Keep stretch goals distinct from the minimum acceptance contract.

### Compatibility and migration

Existing completed feature artifacts remain historical records. Do not rewrite their
approved intent, verification, or hashes to make them resemble newly generated work.

For new cycles, emit the new versioned format. For incomplete 6.x cycles, support either
completion under their existing contract or an explicit migration before resuming.
Migration should preview deterministic ID assignments and references, preserve original
artifacts, and stop on ambiguous mappings. It must not manufacture historical proof or
infer that a previously written checkbox is a verified result.

Require migration idempotence, duplicate-ID detection, interrupted-write recovery, and
a documented rollback before changing the default. Define a support window for old
cycles in the implementation proposal rather than silently dropping compatibility.

### Acceptance evidence for 7.0

Offline tests must demonstrate missing and dangling mappings, valid many-to-many links,
supporting work, multiline criteria, duplicate IDs, reordered requirements, and changed
requirement revisions. Exercise the actual PLAN egress, not only the parser. Verify that
stale evidence cannot satisfy a revised requirement and that historical records remain
unchanged during migration. Review all four harness adapters against the same contract.

## 7.1: maintain current capability specifications

### Separate current behavior from proposed changes

A capability specification describes behavior currently supported by the product. A
feature proposal describes a change against a named capability revision. The proposal
retains its own approved intent and evidence after delivery.

Use explicit add, modify, remove, and rename operations. Removal includes the intended
compatibility or migration behavior. A rename preserves requirement identity when the
behavior is unchanged; a behavioral modification creates a new requirement revision.

This should reduce repeated discovery on brownfield work and make conflicts between
concurrent proposals visible before implementation. It also creates maintenance work,
so introduce it where successive changes benefit from a shared behavioral contract.
Do not require a speculative capability taxonomy for every small maintenance task.

### Synchronization and concurrency

A ready PR has not changed the current product contract. Capability updates must agree
with observed merge state. The implementation design must choose between deltas merged
with their code and a follow-up synchronization change triggered by verified merge
observation. The choice must specify how code and specification revisions stay aligned.

Validate the complete candidate update before publication. Check the expected base
revision, conflicting modifications, duplicate additions, unknown removals, and renamed
identities. Unknown or conflicting state stops publication with evidence; an agent must
not choose whichever version is most convenient.

Publication needs interruption recovery and idempotent replay. Repeated merge observations
must not apply the same delta twice. Multi-file changes need a recoverable transaction
boundary so readers cannot mistake a partial update for a complete contract. Retain
provenance linking the resulting capability revision to the merged change.

### Acceptance evidence for 7.1

Test two proposals modifying the same requirement, compatible independent additions,
stale bases, rename chains, removal conflicts, repeated synchronization, interrupted
publication, and a PR closed without merging. Demonstrate that approved feature history
remains intact and that an unmerged proposal never becomes authoritative current behavior.

Ownership, capability layout, synchronization timing, and cross-repository authority
remain design decisions. Resolve them before enabling this feature by default.

## 7.2: repeat only work whose evidence is no longer valid

### Explicit dependencies and conservative invalidation

Record the declared inputs to a task, verification result, or review: relevant
requirement revisions, artifacts, source and test inputs, commands, configuration,
dependency locks, toolchain identity, and applicable instruction or gate versions.
The exact fingerprint format must be versioned and testable.

Use these declarations to derive affected work at runtime. This is not a stored code
graph, symbol index, or model-generated map of the repository. Declarations are explicit
contracts maintained with their artifacts. If dependency completeness cannot be proven,
fall back to the broader check.

The deterministic driver decides whether evidence is eligible for reuse. A model may
request more work but cannot assert that stale or incomplete evidence is valid. A
requirement change invalidates dependent planning and verification. A changed shared
dependency can invalidate several otherwise untouched tasks. Unknown environment state,
external services, nondeterminism, or unsupported dependency forms require rerunning.

Keep implementation reuse separate from verification reuse. Existing code can still be
useful after its earlier test result expires. Reuse must preserve the provenance of the
original result rather than rewrite its revision to look freshly executed.

### Final integration and recovery

Selective local checks must not replace required checks of the integrated revision.
Preserve the final outcome judge and exact-SHA delivery. Resume continues consumed retry
budgets and reconciles durable results; it must not replenish attempts or hide failed
checks behind an older successful result.

Prototype eligibility as an advisory decision first: report what would be reused while
running the full checks. Compare predictions with observed failures. Enable actual reuse
only for input classes with demonstrated safe invalidation; keep a full-revalidation
override and explain each reuse or rerun decision.

### Acceptance evidence for 7.2

Include edits to code, tests, requirements, shared configuration, lockfiles, commands,
toolchains, and instructions. Test changes outside a declared footprint, missing input
files, corrupt evidence, concurrent updates, interrupted resume, and nondeterministic
checks. A narrow task result must never stand in for repository-wide verification.

## Context and interface improvements across the release

Extend existing phase ingress rather than creating another state or context service.
Where artifacts are large, packets can identify relevant sections, requirements, and
task dependencies. Derive excerpts from current authoritative artifacts, record their
provenance, and allow the agent to read more when needed. Do not summarize away a binding
constraint or present an excerpt as the complete approval record.

Final judging retains the complete approved outcome and boundaries. Compare smaller
packets against the current packets on the same tasks, including cases where necessary
information lies outside the predicted section. Reduced input size is useful only if
missing context does not cause extra repairs or missed requirements.

Simplify the default public command surface around existing primary entry points. Keep
internal phase capabilities available to the driver. Inspect existing shared adapter
generation before introducing a new generator; consolidate only proven duplication.
Installation profiles must preserve standalone usage, resume behavior, and the capability
contracts of Claude Code, Codex, OpenCode, and ADK. Hiding commands alone is not evidence
of lower token consumption.

These changes can land incrementally after measurement. They do not require waiting for
selective verification, and they should not become a reason to delay traceability fixes.

## Release boundaries

Preserve the existing runtime dependency policy, deterministic phase gates, acknowledged
completion, bounded retries, maker/checker separation, approved intent, and exact-SHA
delivery. Preserve current short routes where they remain eligible under the new contract.

Do not replace the graph driver with either external framework. OpenSpec's
[artifact completion detection](https://github.com/Fission-AI/OpenSpec/blob/9d4e5974e5c0d9a09b9c6c1e1eb0975e80ec4461/src/core/artifact-graph/state.ts)
uses artifact existence for planning status; that does not establish execution success.
Spec-kit's [convergence command](https://github.com/github/spec-kit/blob/c173bf19a6654e3b05386ec3599349a55282b897/templates/commands/converge.md)
offers traceable follow-up work, but loop-spec already has an outcome judge and recovery
queue. Another convergence phase would need independent evidence of value.

Do not add mandatory documents or review rounds merely to imitate another repository.
No new daemon, database, embedding store, or persistent code map is part of this proposal.
No automatic merge or paid live evaluation is authorized by this planning document.

## Evaluation and promotion criteria

Use the merged 6.5.0 baseline and candidate revisions on a fixed task set. Include small
maintenance, bounded bugs, new features, successive changes to an existing capability,
concurrent proposals, and interrupted runs. Keep task inputs, model settings, harness
versions, and environments comparable; record differences rather than hiding them.

| Measure | Definition and purpose |
|---|---|
| Cost per verified delivery | Total spend across all attempted runs divided by successful verified deliveries; failed attempts count toward cost. Report no-success cohorts explicitly. |
| Completion rate | Successful verified deliveries divided by all attempted runs, with blocked and failed runs classified. |
| Elapsed time | End-to-end time, including repairs and retries; report median and tail behavior where sample size permits. |
| Human intervention | Count requests and corrective actions needed to reach delivery. |
| Repeated work | Phase invocations, tool calls, repair rounds, and checks repeated after revisions. |
| Context use | Input/output tokens and relevant cache statistics where observable; separate these from disk snapshot size. |
| Outcome quality | Independent review of original intent, regression behavior, and evidence validity. |

Predeclare sample sizes, acceptable completion-rate variation, and minimum useful savings
before running comparative evaluations. Numerical targets remain open until baseline
variance and task costs are known. Do not pick thresholds after seeing favorable results.
Report results per task class and harness so aggregate savings do not hide regressions.

Offline checks establish parser, gate, migration, synchronization, and invalidation
behavior. They cannot establish model cost or live completion. Follow
[the evaluation guide](../../evals/README.md) and obtain separate authorization before
paid runs. Preserve raw run evidence under the existing evaluation policy.

Promote each optimization only when the agreed evidence supports it. If selective reuse
fails its criteria, retain full verification while shipping the independently useful
traceability work. If a smaller packet increases repairs, retain the broader packet.

## Implementation order and decisions to close

| Stage | Deliverable | Depends on |
|---|---|---|
| Baseline | Reproducible coverage regression and a comparative evaluation design | Merged 6.5.0 |
| 7.0 foundation | Criterion-to-task gate, stable IDs, scenarios, evidence references | Artifact grammar and ownership decisions |
| 7.0 migration | Versioned readers, migration preview, preserved historical records | Stable identity contract |
| 7.1 lifecycle | Capability deltas, conflict checks, merge-aligned synchronization | Revision identities and publication design |
| 7.2 experiment | Advisory invalidation, then narrowly eligible evidence reuse | Proven dependency declarations and evaluation results |
| Cross-cutting | Smaller context packets and simpler discovery | Harness compatibility and measured benefit |

Before implementing each stage, create its feature specification and plan through the
existing cycle. That work must settle the exact artifact grammar, compatibility window,
capability ownership and storage, publication mechanism, evidence identity, and evaluation
thresholds relevant to the stage. This roadmap is the rationale and release sequence;
it is not a substitute for approved implementation contracts.
