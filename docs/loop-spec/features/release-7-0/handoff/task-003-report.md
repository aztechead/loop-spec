## Consumer contract

The module header in lib/artifact_publication.py defines the capture, stage, publish, and recovery interface. The CLI uses capture/publish/recover with --feature-dir, and publish additionally requires --token and --manifest. The manifest is an object with version 1, files containing source/target pairs, and updates containing path/value pairs. Stage sources live under publication-staging; targets are registered logical artifact keys. The Python stage function accepts generated bytes and returns a manifest source.

CLI target registration covers spec, plan, patterns, verification, and tasks, with canonical defaults before the first artifact pointer exists. Existing absolute pointers are accepted only within the feature state/docs roots. Git and canonical non-Git workspace layouts work. Metadata strings are not file registrations. CLI state updates permit warnings only. Trusted controllers may supply a validated registry and an explicit allowed_updates set; phase acknowledgement is tested through that seam, and direct CLI phase/control-field edits are rejected.

Tokens bind publication generation, the state digest, and registered input paths/hashes. Producers retain ingress tokens across work; only their accepted publication returns a refreshed token. feature-write accepts an explicit final --token PATH and returns a refreshed token after its own accepted state write. Transitional ordinary tokenless writer behavior remains available. Metadata writes increment the CAS generation without advancing evidenceEpoch. Neither publication nor recovery holds a lock across producer work.

A relocated controller with persisted absolute task pointers passes registry={"tasks":"tasks.json"} to capture/publish/recover until it updates that pointer. The registry is bound into capture's input mapping; publication cannot redirect it. Journals use logical target keys, and the relocation test proves recovery changes only the resumed checkout. The consumer seam is real and exercised; task 004 owns attaching it to production source callers.

Interrupted transactions retain immutable originals and a journal in publication-generations. Recovery validates every original and every current target against its before/expected-after hash before mutation, refuses later user edits, and restores originals while advancing generation. State-ref preserves observation, migration, and publication recovery trees plus exact file permissions. Mirror tests cover actual interrupted transaction reopen and recovery.

## Design and scale review

The deployment controls file bytes, registered paths, and competing writers. Hashing streams in 64 KiB chunks; staged/replaced artifacts and CLI token/manifest JSON use bounded 16 MiB reads, transactions to 64 MiB of old/new artifact bytes and 256 files/updates. Work is linear in hashed bytes plus transaction size. Existing feature-state JSON remains loaded as one document, as in the state writer's prior contract.

The state writer retains preparation, atomic replacement, and persistence. Publication receives target/update registries and failure callbacks and uses those state primitives in process. The four design questions were checked before implementation and again after verification: no extra coordinator, runtime dependency, migration conversion, or observation producer was added. Reused stdlib locks, hashing, and the existing durable file publisher; skipped speculative callers.

## Rework attempt 1: repeated recovery interruption

The reviewer demonstrated that a recovery could write its state, fail its completion rename, then overwrite the accepted recovery hash on a retry that failed before writing state. A third attempt incorrectly rejected the state written by the first attempt.

The new regression exercises both second-failure boundaries: store persistence before the state write and the state write itself. It also inserts a later user edit, verifies refusal, restores the legitimate recovered bytes, and completes the real recovery. The initial run failed with:

```text
ValueError: recovery refuses changed target: .../recovery-persist/feature.json
```

Recovery now reuses its durable recoveryGeneration and verifies that recomputing the restored state produces the recorded recoveredStateHash. It chooses that pair only on the first recovery attempt. Retries neither advance the selected generation nor replace its accepted hash. The selected generation remains greater than the interrupted publication generation, and current state cannot exceed it. Storage remains constant: one generation and one recovery hash, without retry history.

The four design questions were checked before and after this fix. The existing journal already owns the required durable choice; no helper, new dependency, lock, or unbounded retry collection was needed. The change is confined to recovery selection and its regression.
